# 0021: Structured JSON log files, GDPR-constrained, shipped to Loki

- Status: Accepted
- Date: 2026-09-23
- Scope: Required (v1)
- Supersedes: v1 ADRs 0005, 0061
- Related: [0009](0009-tu-id-identity-model.md), [0013](0013-gdpr-export-and-retention.md), [0022](0022-observability-and-alerting.md), [0023](0023-secrets-management.md), [0024](0024-background-jobs-bullmq.md)

## Context

Logs are the primary diagnostic surface and simultaneously the easiest place to accumulate personal data by accident. They also need to reach Loki identically in local, CI and production environments.

## Decision

### The application writes structured log files

The API, the worker and the backup service write **newline-delimited JSON** to log files on a shared, dedicated volume (one file per service), and the same stream to stdout.

- The file is what the collector reads. Making it a file rather than container output is deliberate: it keeps the application's structured lines independent of how the container runtime handles output, and reading a mounted file is identical in every environment. The parity rule in [0001](0001-one-stack-every-environment.md) is only real if the collection path is the same everywhere. (This ADR first assumed Compose and Quadlet differ in log driver; under Podman both log to journald, which is what makes the collection of third-party output below uniform too.)
- Stdout remains for interactive use during development.
- Files are rotated by size with a bounded number of kept files, so a log volume cannot fill the host: `<service>.<n>.log` on the `logs` volume, 10 MB each, the current one and five more per service. The volume belongs to the api's user; the backup service, which runs under a UID of its own ([0017](0017-nfs-backup-storage.md)), writes into a directory `backup/` on it, which its container creates as root at start before dropping to that UID.

Logger: **pino**, for JSON output and a redaction mechanism that is configured once rather than remembered at each call site.

### Every entry carries

`timestamp`, `level`, `service`, `request_id`, `route`, `status`, `duration_ms`, and `user_ref` where a request is authenticated. Errors additionally carry the error type and stack.

`request_id` is generated by the API per request and propagated to WebSocket calls, to audit events and to jobs enqueued by the request ([0024](0024-background-jobs-bullmq.md)), so a user-reported problem can be traced across all three.

- Its format is a W3C `traceparent` trace-id: 32 lowercase hex digits ([0022](0022-observability-and-alerting.md)). Nginx's `$request_id` has exactly that shape, so Nginx sends it as `X-Request-Id`, writes it into its access log, and the API keeps it — only from Nginx's own address and only when well-formed, like `X-Forwarded-For` ([0016](0016-nginx-and-tls-everywhere.md)). Otherwise the API generates one. The response names it in `X-Request-Id`, so a user can quote it.
- Each WebSocket call is its own request with its own id.
- Every request, HTTP or WebSocket call, ends in one line with message `request`: `route` as a template (`/api/users/:id`, or `unmatched`, never a raw path), `method` (the HTTP verb, or the Feathers method over the WebSocket), `status` and `duration_ms`. Every line written while a request runs carries its `request_id`, and `user_ref` once it is authenticated. `level` is the textual level (`info`, `error`).

### What must never appear

Enforced by pino's redaction configuration, not by discipline:

- passwords, tokens, refresh cookies, session hashes,
- SAML assertions or any part of them,
- request bodies of authentication and user-management endpoints,
- secrets of any kind ([0023](0023-secrets-management.md)).

### GDPR constraints on log content

- `user_ref` is the **surrogate user key**, never the TU-ID, per [0009](0009-tu-id-identity-model.md). Logs therefore contain no direct identifier, which is what makes a 14-day retention defensible without a per-record erasure path.
- Client IP addresses appear only in security events (failed authentication, rate-limit rejections), not in ordinary request logs.
- Log retention is **14 days**, enforced by Loki's compactor rather than by the application ([0013](0013-gdpr-export-and-retention.md)). It is deployment configuration of Loki, not a runtime setting, because Loki reads it from its own configuration.
- An erasure request does not require log rewriting, because logs hold no direct identifiers and expire within the retention window.

### Collection

**Grafana Alloy** runs as a container, tails the log volume, and pushes to Loki over TLS. (Promtail was the original choice; it reached end of life on 2026-03-02, and Alloy is its successor from the same vendor.) Labels are low-cardinality only — `service`, `level`, `environment`. `request_id` and `user_ref` stay JSON fields inside the line and are never promoted to labels; doing so would create one Loki stream per user and make the store unusable.

Third-party containers (PostgreSQL, PgBouncer, Garage, Keycloak) do not emit JSON. Their output is collected as plain text and labelled by service. This is accepted rather than worked around. Alloy reads it from the host user's journal, where Podman logs container output under Compose and Quadlet alike, labelled by container name; the API's and the worker's own output is taken from their files only, not twice. These lines carry no `level` label: stderr is not an error level.

## Consequences

- One collection mechanism across all environments, so the logging pipeline is exercised from the first local run.
- A log volume must be sized and rotated; an unrotated JSON log is a disk-exhaustion vector.
- Logs are pseudonymous, so answering "what did this specific person do" requires the audit events in [0013](0013-gdpr-export-and-retention.md), not the logs. That is the intended division.
